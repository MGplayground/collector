# Codebase audit — August 2026

Full read of every file in `src/`, checked against the live database. Findings are
ordered by what a user would notice, not by how interesting they are to fix.

The headline: the app has no defect *detection* layer at all — no working linter, no
tests, no CI. Every bug found below was found by reading, which is why they have
survived. The system proposal at the end matters more than any individual fix.

---

## Severity 1 — the app is currently showing wrong numbers

### 1.1 Analytics counts your watchlist as your portfolio

`src/services/analytics.js:10`

```js
const owned = items.filter(i => i.status !== 'sold')
```

A watchlist item is something you do **not** own. Naming the variable `owned` hides
that `totalValue` (headline "Portfolio value") and `totalInvested` ("Cost basis")
both include items you are only tracking.

This is not theoretical. Every row in the live database is currently on the
watchlist, and none has a purchase price:

| status | items | Σ current_value | Σ purchase_price |
|---|---|---|---|
| watchlist | 5 | £2,148.59 | *null* |

So the Analytics tab right now reports a **£2,148.59 portfolio with a £0 cost basis
and a £2,148.59 unrealized gain** — on five items the app has been told you don't
own and didn't pay for.

**Contributing cause:** `ItemForm` defaults new items to `status: 'watchlist'`
(`src/components/collection/ItemForm.jsx:9`). For a collection tracker, the common
case is something you just bought. The default is fighting the app's purpose, and
it is why all five rows ended up there.

### 1.2 Every gain figure in the app is blank

A consequence of the same data state, but worth naming separately because it makes
four features silently inert:

- `ItemCard` gain % — `gainPct()` returns null when `purchase_price` is null
- `ItemDetail` gain/loss stat — hidden entirely
- `GainersLosers` — `withGain` filters on `purchase_price &&`, so it is empty
- Collection's "Biggest gain %" sort — nothing to sort

None of these are broken code. They are all correctly rendering "no data" for a
field nothing populates, which is exactly the kind of failure no error message will
ever tell you about.

### 1.3 Sold items keep counting toward portfolio value forever

`src/services/analytics.js:93`

```js
items.forEach(item => { ... })   // every item, including sold
```

`buildPortfolioTimeline` iterates all items with no status filter, while the hero
stats above it exclude sold. The chart and the number above it are computed from
different populations, so they will disagree the moment anything is sold. Nothing
is sold yet, so this is latent — it will surface as "the chart doesn't match the
total" on the first sale.

## Severity 2 — failures that happen silently

### 2.1 A failed save looks identical to a successful one

`src/components/collection/ItemForm.jsx:69`

```js
try {
  await onSave(toPayload(form))
  onClose()
} finally {
  setSaving(false)
}
```

`try/finally` with no `catch`. `useItems.create/update/remove` don't catch either,
and the services re-throw. So when an insert is rejected — a CHECK constraint, an
RLS denial, an expired session, offline — the spinner stops, the modal stays open,
nothing is said, and the rejection surfaces only in the console.

This is the single most likely source of "it didn't save and I don't know why", and
it got riskier with the new `item_type` CHECK constraint.

### 2.2 The error banner never clears

`src/hooks/useItems.js:31` sets `error` on failure but no path ever sets it back to
`null`. One transient network blip and the red banner stays on the Collection page
for the rest of the session, including after successful refetches.

### 2.3 The compensating rollback can fail silently

`src/services/priceHistory.js:30`

```js
await supabase.from('price_history').delete().eq('id', inserted.id)
```

The result is discarded. If the compensating delete fails, `logPrice` throws the
original error and leaves behind exactly the orphaned row the rollback exists to
prevent — with no signal that it happened. The invariant is right; its failure mode
is invisible.

## Severity 3 — consistency drift

### 3.1 Three different money formatters

Each component defines its own `fmt`:

| Same value | `ItemCard` | `ItemDetail` | `VaultTile` |
|---|---|---|---|
| `1050` | £1,050.00 | £1,050.00 | £1,050 |
| `119.95` | £119.95 | £119.95 | £119.95 |
| `1050.005` | £1,050.01 | **£1,050.005** | £1,050.01 |

`ItemDetail` omits `maximumFractionDigits`, which defaults to 3 — so a computed
gain can render three decimal places of pounds. The Vault formatter (mine) drops
trailing zeros. Nobody decided this; it accumulated.

### 3.2 Label maps duplicated four times

`CAT_LABELS` is redefined in `ItemForm`, `ItemFilters`, `VaultTile`, and `Badge`.
Status labels are built ad hoc with `.charAt(0).toUpperCase()`. Adding a category
means finding four files, and missing one degrades silently to a raw enum string.

This is the same class of defect as the "raw" caption bug caught during Vault
testing: presentation logic derived independently in each component, drifting apart.

### 3.3 No error boundary

A render-time throw anywhere unmounts the whole tree to a blank screen. In an
installed PWA with no address bar, a white screen is indistinguishable from a
crashed app, and the only recovery is force-quit.

### 3.4 Floating-point money

All arithmetic is `Number` on `numeric(10,2)` columns. Display is safe —
`toLocaleString` rounds, so `119.94999999999993` renders `£119.95` — but summing
hundreds of values in `analytics.js` can drift by pennies. Low priority at five
items; worth knowing before it is five hundred.

## Severity 4 — the missing safety net (root cause)

| | Status |
|---|---|
| `npm run lint` | **Has never worked.** No `eslint.config.js`; ESLint 9 requires flat config. Fails identically on `main`. |
| Tests | **None.** No runner, no test files. |
| CI | **None.** No `.github/` directory. |
| Type checking | None. `@types/react` is installed but nothing runs `tsc`. |

Every Severity 1–3 finding above would have been caught cheaply:

- 1.1 and 1.3 — one unit test on `getAnalyticsData` with a watchlist fixture
- 2.1 and 2.2 — one component test asserting an error message appears
- 3.1 — impossible to write twice if there is one `formatMoney`

Bundle is also 890 KB in a single chunk (248 KB gzipped). Recharts is the bulk of
it and is only needed by `ItemDetail` and `AnalyticsPage`, both of which mount on
demand.

## The system

Four layers, cheapest first. The point is that each one makes a whole *category* of
bug impossible rather than fixing one instance.

### Layer 1 — one source of truth per concept

```
src/domain/
  money.js      formatMoney, gain, gainPct        — the only place £ is rendered
  item.js       categories, statuses, item types, their labels, and
                isSealed / isSlabbed / gradeLabel — the only place an enum is named
  portfolio.js  what counts as owned, what counts toward the portfolio
```

`portfolio.js` is the important one: it makes "does a watchlist item count?" a
single answerable question with one answer, instead of a filter re-derived in five
places. Findings 1.1, 1.3, 3.1 and 3.2 all collapse into this layer.

### Layer 2 — make failure loud

- An `<ErrorBoundary>` around the routed area, with a reload affordance
- A `catch` in `ItemForm`, rendering the message inline above the actions
- `setError(null)` on every successful fetch
- Log the compensating-delete failure in `priceHistory`

### Layer 3 — tests, in the order they pay off

1. **Unit — `getAnalyticsData`.** Pure function, no mocking. Fixtures for
   watchlist, sold, missing purchase price. Locks findings 1.1 and 1.3 shut.
2. **Unit — `toPayload` and the domain helpers.** Sealed writes `is_raw: true` and
   null grades; graded cards keep theirs.
3. **Component — `ItemForm` save failure shows a message.**
4. **E2E — Playwright against a stubbed Supabase.** I already built this harness to
   verify the Vault; it drives real login, the view toggle, upload with real
   compression, and asserts the exact insert payload. It should be committed rather
   than thrown away.

Vitest + React Testing Library. No new runtime dependencies.

### Layer 4 — automate it

- `eslint.config.js` so `npm run lint` runs at all
- `.github/workflows/ci.yml` — lint, test, build on every PR
- Lazy-load `recharts` via `React.lazy` in `ItemDetail` and `AnalyticsPage`

## Suggested order

| # | Work | Why here |
|---|---|---|
| 1 | Fix 1.1 + 1.3, with the tests that prove them | Wrong numbers on screen right now |
| 2 | Layer 2 — loud failure | Stops the next bug being silent |
| 3 | `eslint.config.js` + CI | Cheap, and everything after benefits |
| 4 | Layer 1 — domain extraction, component by component | Refactor under test coverage, not before |
| 5 | Commit the E2E harness | Regression net for the next feature |
| 6 | Bundle split | Pure performance, no correctness risk |

One product question blocks item 1: whether those five rows are genuinely watchlist
or should be `owned`. The code fix and the data fix are different work.
